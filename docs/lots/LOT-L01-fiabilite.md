# Fiche LOT-L01 — Fiabilité des téléchargements : coupure réseau, disque plein (Windows)

- Statut : Fait (bureau) ; Android : reprise et messages partagés, attente du réseau non disponible (la plateforme ne sait pas dire s'il y a une route)
- Exigences CDC : PAR-04 (coupure réseau → retour → reprise ; sinon redémarrage explicitement proposé), DL-01 (état durable), DL-02 (reprise selon la source : jamais de concaténation corrompue), DL-04 / T-05 (disque plein, accès refusé, aucun écrasement)
- Maquette : `design/design_handoff_windows_v2` écran 3 (lignes « Connexion perdue · nouvel essai », « reprise à 34 % ») et scénario « hors ligne » (bandeau `wifi_off` « Vous êtes hors ligne. Les téléchargements sont en pause et reprendront au retour du réseau », résumé « En pause · hors ligne »)
- Inclus :
  - Reprise vérifiée (lien direct HTTP) : au début d'un téléchargement, l'identité du fichier distant (ETag fort, sinon Last-Modified, et taille) est écrite à côté du fichier partiel (`.part.id`). À la reprise, la requête envoie `Range` et `If-Range` : si le fichier a changé, le serveur renvoie le fichier entier, qui remplace les octets partiels. Une réponse partielle dont la taille ou l'ETag diffère fait repartir de zéro. Un fichier partiel sans identité (ancienne version, identité perdue) n'est jamais continué : il repart de zéro. Un ETag faible n'est pas utilisé pour `If-Range` (la taille sert alors de contrôle). L'identité est supprimée à la fin, à l'annulation et au redémarrage.
  - Coupure réseau : quand une erreur de transport survient et que Windows n'a plus aucune route réseau (câble débranché, Wi-Fi coupé, mode avion ; simple lecture de la table de routage, aucun paquet envoyé), la tâche attend le retour du réseau sans dépenser ses essais, puis reprend seule depuis ses octets. Avec une route mais une source muette, le comportement reste le même qu'avant : 5 essais espacés, puis échec avec reprise possible.
  - Disque et dossier : contrôle d'espace avant de relancer une tâche dont la taille est connue (un « Réessayer » sans place libérée échoue tout de suite, sans retélécharger) ; nouveau cas « accès refusé » (`access_denied`) distinct des autres erreurs de fichier ; messages Windows de yt-dlp reconnus (« There is not enough space on the disk », WinError 112, « Access is denied », Errno 13).
  - Machine d'états : « En attente → Échec » est maintenant permis. Avant, une tâche dont le dossier ne pouvait pas être créé (ou sans place) restait bloquée « En attente ».
  - « Recommencer depuis le début » (commande `downloads_restart` + permission) : proposé sur une ligne en échec qui a gardé des octets ; supprime le partiel et relance à zéro.
  - Interface : ligne « En pause · hors ligne » (icône `wifi_off`) pendant l'attente du réseau ; carte de la barre latérale et accueil mobile « En pause · hors ligne » ; bandeau hors ligne avec le texte de la maquette (désormais vrai) ; échecs « disque plein » et « dossier non accessible » avec l'action à faire (« libérez de l'espace puis réessayez », « choisissez un autre dossier dans Réglages ») ; FR / EN.
- Adaptations :
  - « octets vérifiés » (maquette) n'est pas affiché : seule la reprise HTTP directe vérifie l'identité ; pour yt-dlp, la reprise est la sienne (`--continue`). La ligne garde « reprise à N % ».
  - « Recommencer depuis le début » est une 4e icône sur les lignes en échec qui ont des octets gardés (la maquette n'a que réessayer / dossier / annuler).
  - Après un rechargement de l'interface pendant une coupure, la ligne affiche « En attente » jusqu'au retour du réseau (l'attente n'est pas stockée) ; le bandeau, lui, suit l'état du réseau.
  - Les causes connues des échecs (disque plein, espace insuffisant, dossier non accessible) sont traduites dans Téléchargements et Historique ; les autres causes restent le texte du moteur (anglais).
- Tests : `cargo test -p download-engine` (moteur 48, HTTP 14, gestionnaire 13 — nouveaux : reprise avec If-Range, fichier changé jamais recollé, taille changée sans validateur, Last-Modified, ETag faible, partiel d'origine inconnue, attente du réseau sans essai dépensé, recommencer, réessai refusé faute d'espace ; messages yt-dlp Windows ; accès refusé), `cargo test -p media-core` (40, En attente → Échec), `vitest` 31 fichiers, 165 tests (ligne et carte « En pause · hors ligne », échec « dossier non accessible » + aide + « Recommencer », causes traduites) ; clippy sans nouvel avertissement.
- Recette native Windows (build release isolé, serveur HTTP local avec ETag / If-Range, fichier de 20 Mio) :
  - coupure de la connexion à 3 Mio : nouvel essai automatique avec `Range: bytes=3145728-` et `If-Range: "v1"`, fichier final identique (SHA-256), aucun `.part` / `.id` laissé ;
  - pause à 6,2 Mio, fichier distant remplacé (ETag v2), reprise : le serveur renvoie le fichier entier, le résultat est exactement la v2 (aucun octet de la v1) ;
  - taille annoncée de 10 Tio : échec « espace insuffisant » avant tout octet, sans essai ;
  - « Recommencer » après une pause : requête sans `Range`, fichier exact ;
  - dossier de destination interdit en écriture (ACL temporaire) : échec `access_denied` immédiat, « Échec · dossier non accessible » + « choisissez un autre dossier dans Réglages » ; accès rendu puis « Réessayer » : fichier exact.
- Non testé : vraie perte du réseau (couper le Wi-Fi de la machine aurait gêné l'utilisateur ; couvert par test automatique avec une sonde simulée), vrai disque plein en cours d'écriture (pas de droits administrateur pour un disque virtuel ; couvert par tests de classement des erreurs).
- Non inclus : écriture durable des octets en cas de coupure de courant (seul un arrêt du processus est couvert), lecture blanche (traitée le 31/10), Android (attente du réseau, permissions révoquées), URL expirée pour les liens directs (échec HTTP, « Recommencer » proposé).
- Retour arrière : revert ; un fichier `.part.id` laissé par cette version est ignoré par l'ancienne.
